# 跨 batch 序列缝合：输入、分段与容量约束研究

本文是主规格冻结前的只读实现研究，不是已实现或已验证声明。源代码基线为 `56a0ea1`。
用户已授权完整实现；本文仅修改本研究文件，生产代码、测试和权威规格由后续分工处理。

## 范围与最小路径

输入仍是有限文件集合。会话边界仍由现有摄取规则确定；不引入实时接入、跨进程恢复或跨会话合并。
同一会话的分段、线索状态和容量封闭状态覆盖全部计算块。`run.batch_size` 不再决定序列边界。

```mermaid
flowchart LR
    I[已有完整 Session] --> W[按完整会话规划有重叠的分段窗口]
    W --> E[按声明序结算噪声与语义片段]
    E --> C[完整成员容量检查与必要分区]
    C --> P[同一会话持续推进线索候选]
    P --> G[合并预览与完整证据容量检查]
    G -->|可装| M[提交线索成员变更]
    G -->|不可装| S[封闭旧线索并保留后段]
    M --> R[仅对未封闭线索执行复评]
    S --> R
    R --> D[会话结算后交给下游]
```

最小端到端版本可以保持 M2 交付完整会话，复用当前 segment 的全会话窗口规划和有界执行器，
让 stitch 的工作状态在一个会话的所有计算块之间持续存在，且只在会话结束执行复评和最终元数据结算。
它不要求把摄取接口改成开放会话增量事件；完整会话原本就已缓存在内存中。

不能把仅删除硬切分支描述为全部需求已经满足：还必须明确计算块派发、成员容量预检、不可再合并的
封闭状态、下游真实请求检查、有限重算、稳定随机源、校准边界、计量与中断的契约。

文本 `input_order` 换文件也结束会话，`meta:*` 模式下文件边界透明；这次不能隐式扩大为跨会话能力。
证据为 `ingest.py:717-728,842-862` 和 `spec/302-m2-ingest.md:166-176`。

## 输入与计算块的接口处理

保留 `Ingestor.sessions()` 与 `Session`。编排层为每个 Session 建立一份帧信封列表和稳定的会话声明序号，
同一帧信封在分段、救援、复评、验证和最终路由中使用同一个对象。M2 的 Record 仍共享引用，图像仍懒加载。

`batch_size` 在序列处理模式中的计算块含义必须由主规格统一冻结。可直接复用的最小方式是把已经规划的
叶任务分组派发：segment 的窗口、extract 的相邻对、逐成员标注的请求保持各自原子单位；一次分组的变化
不能重新划分语义序列。若仍以帧作为计算块单位，跨块窗口也必须来自全会话固定计划，而不是块内重建。

建议为序列模式新增独立的会话驱动方法，普通单记录路径继续使用现有 `_dispatch`。序列驱动从现有
`_run_chain` 提取阶段调用、耗时和指标的公共方法，避免复制完整生命周期；阶段执行与最终 emit 分离。
同一会话只在其全部线索稳定并经过下游后进入最终状态清点，不能每个计算块重复清点吸收帧和 stitched 壳。

不把多个完整会话塞进同一随 `batch_size` 改变的语义处理范围。最小实现可顺序处理会话；如果保留跨会话
并发，必须先固定与 batch 无关的会话执行周期和图像校准快照，不以并发完成顺序冻结预算。

## 分段与初次超长片段

直接复用 `_plan_windows`、`_run_window` 和窗口声明序归并；原有 `_judge_span_degrading` 已实现真正
reactive overflow 的有限二分且保留接缝重叠，属于可复用的有界请求拆分逻辑。

完整会话的关系表结算后，先按原有语义规则剔噪、切段并执行 `min_len`。再对每个保留段做完整成员容量
检查，必要时在成员边界分区，最后调用 `_emit_episode`。不要先生成一条 episode、更新 counts 和成员归属，
再把它拆成若干信封；那会引入壳、重复计数和无用的原始 ID。

容量分区必须满足：

- 保留成员按原会话顺序形成不相交分区；无遗漏、无重复，不复制前块尾帧为后块业务成员。
- 计算块边界不参与分区决定；预算快照、完整实际证据与已冻结的最小单位才是输入。
- 容量尾块即使短于 `segment.min_len` 也不能被再次当作语义短段丢弃；原段已通过语义检查。
- 每个新 episode 的 ID 在 `_emit_episode` 中由自身最终成员推导，session ID 保持原值。
- 容量分区产生的前段在进入 stitch 时即封闭；否则 pass1/pass2 会把容量边界重新消除。
- 对一次语义片段的容量拆分，必须记录容量边界原因，不伪装成 LLM 发现的任务边界。

主规格已选择完整成员帧为容量切分的最小单位，连同该调用需要的该帧载荷完整保留。
segment 自身的边界判断最少需要相邻两帧，extract 最少需要一个完整相邻对；不能把这些请求拆成缺少
判定证据的单帧调用。下游序列可在帧边界切分，但不能声称仍推断了被切开的跨分区动作。
若连所需完整最小单位也装不下，必须失败并保留精确阶段和 `context_overflow` 归因；不可通过裁剪正文、
摘要替代、丢中间帧或静默缩图数量来声称满足完整证据要求。

## 合并、救援与复评的容量闸门

容量判断必须共用实际请求构造与实际 Schema 选择，复用 `budget.est_prompt`、`input_budget` 和现有
LLMClient 终检公式。不能在 stitch 中复制另一套下游字符数估计，也不能用摘要卡长度代替全部成员证据。

建议在 common 的阶段契约中声明小型容量检查协议，由编排层组合各算子提供的真实请求规划函数，并交给
序列 RunContext。这样 stitch 只调用 common 协议，不反向导入 orchestration 或依赖其他算子的私有函数。
无需新增可插拔注册表、配置层或第三方依赖。具体命名由主规格与下游分工统一。

每次变更使用两阶段的本地顺序：先基于成员和碎片构造无副作用候选视图，检查其完整证据请求预算，
通过后才重绑 Record、更新 fragments、状态、rescued_by 和计数。候选预览不得浅拷贝后直接修改共享成员
字段；可复用不可变 Record 的 `dataclasses.replace`，帧信封保持正式对象直到提交。

| 入口 | 可装 | 不可装 |
|---|---|---|
| 新开 episode | 建立开放线索 | 上游先做完整成员分区；最小单位不可装则失败 |
| pass1 接续 | 一次提交成员、碎片和候选壳状态 | 封闭旧目标，候选保留自身线索 |
| 短段救援 | 一次提交成员归属与 rescued_short | 封闭旧目标；短段仍保持原 dropped_noise，不凭容量失败新建任务 |
| pass2 复评合并 | 一次提交目标重绑与候选壳状态 | 原有两条线索保持独立；按会话时序封闭较早那条 |

主规格已采纳救援容量失败维持 dropped_noise；这是现有 rescue 永不新开线索的契约延续
（`stitch.py:784-785,984-988`），不能把“保留后段”解释成新增 rescue 开线索行为。

建议 `_Thread` 增加 `sealed` 与封闭原因；`alive` 继续表示是否为存活输出线索，不能兼任 sealed。
容量封闭从 pool 移除，且须同时覆盖 `_prepare_repass` 的候选、`_next_repass_plan` 的再次检查、
`_repass_pool` 的目标，以及统一提交入口的最终不变量。当前普通池淘汰是否仍允许复评由现有契约保持，
容量封闭不能与它混用。最终 `_finalize_session` 仍处理所有 alive 线索，包括 sealed。

pass2 允许目标在候选之后，故“旧段”必须按实际成员会话位置定义，不能简单认定目标总是旧段。
容量不足时双方均不修改，较早线索封闭；后续每次合并仍重新检查预算。对交错跨度不能建立严格早晚时，
可将双方封闭并明确该规则，或者采用最早成员位置作为确定性顺序；主规格必须选择一种，不留实现者猜测。

## 身份、成员归属与派生元数据

保持原生存规则：pass1 创始信封存活，pass2 目标信封存活，合并后存活 record ID 不重算。
只有容量分区创建新 episode 时才计算各自成员哈希。失败容量预览不得留下 thread_id、stitched 状态、
rescued_by 或片段归因；成功后每个帧信封仍至多归一个存活序列。

当前 `position_of` 用 `record.id` 首次出现的位置（`stitch.py:758-760`）。内容相同的不同输入出现位置可能
拥有相同 ID，因此新跨块逻辑不得再用 ID 集合去合并、去重或重建归属。建议在会话驱动中建立按输入出现位置
索引的帧表，位置到原始帧对象是唯一归属事实；stitch 的片段跨度与 seam 计算都使用这些稳定位置。
如果主规格选择新增成员位置载体，应同步帧标注与 verify 回收接口，而不是只在 stitch 内补一个临时映射。
现有 `member_classifications`、帧标注字典以 ID 键控的语义是否需要扩展，应由主规格明确，不能假定当前
ID 语义天然能够区分重复输入出现位置。

封闭元数据应在最终产物中可审计，但不需要新增落盘通道。删除原有“因 batch 硬切”的 session_split
语义、静态警告、verify 降级条件及对应旧测试；不能把 context_capacity 冒充 session_split。

## 实际溢出与未提交重算

提前检查只能精确计量当时已经确定的证据。stitch 阶段还没有 extract 结果、选类结果以及标注/后处理结果；
因此不能声称一次提前检查就精确保证所有后续调用。分类未知时应检查所有可达类的实际指令和模型 Schema；
后续生成的值必须在真实请求构造后再检查。

主规格已冻结预检承诺仅覆盖已知完整原始证据及当前实际模板、Schema 开销；未知分类、摘取、标注与
后处理结果通过真实请求预算检查和提交前的会话重算闭合。验证提示词会包含实际标注结果；
确定性 postprocessor 的产物大小也不必受模型输出 token 上限约束。
不得仅通过预留 `max_output_tokens` 证明最终 verify 请求必然可装。实际请求的完整检查必须保留，
并在还未提交的序列范围内允许有限拆分重算或最小单位失败。

现有 reactive overflow 有 `phase` 和 `origin`，应复用其归因及熔断恰一次机制。只重算未提交的候选状态；
已输出、已正式 dedup 提交或已计入最终数据计数的内容不可被回头切分。调用用量与失败证据保留，
候选 annotation、classifications、transitions、成员状态与正式计数必须隔离并能丢弃。
该提交边界需要由下游设计与编排主规格共同闭合，单独修改 stitch 不足以保证。

## batch 无关的随机源与校准

当前 segment/stitch 不消费 `ctx.rng`，但 quality 的配对规划消费它（`quality.py:171-190,900-910`）。
仅修改 seed 字符串还不够：quality 比较池也不能随物理计算块重新划分。

主规格已选择序列模式以稳定的会话声明序与阶段名派生 RNG、task namespace、任务声明 key；会话内候选时钟、
窗口跨度与 vote 序号继续作为叶任务身份。物理块号仅用于调度和可选进度，不进入业务随机源与成员身份。

主规格已选择图像校准以完整会话作为冻结周期：会话开始读取上一个已完成会话的快照，同一会话所有阶段以及
LLMClient 最终终检读取同一份快照；会话结束后再折入新样本。不能只让上游规划冻结，真实请求终检仍
读取按计算块更新的快照。普通 record 模式现有批校准可保持；序列模式需要明确独立的冻结周期命名和报告。

如果保留跨会话并发，建议先冻结与 batch 无关的会话组边界或使用显式不可变预算快照下传；
不可按最先完成的会话刷新全局校准器而影响其他在飞会话。最小端到端实现顺序处理会话可避免这一耦合。

## 主规格需要明确的收敛点

- `batch_size` 在序列模式的精确计算分组单位，以及日志中的 batch 与会话范围怎样表述。
- 容量边界的外部表示，以及跨该边界的动作是否明确不产生；最小单位完整帧已确认。
- pass2 交错跨度容量失败时按最早成员封闭一条，还是封闭双方。
- 重复内容 ID 的成员出现位置是否需要统一载体，帧产物现有按 ID 键控的语义如何保持准确。
- 对生成后才知道大小的证据，未提交范围与最大拆分重算次数，以及正式 dedup/输出的提交位置。

这些是必须在实现前冻结的行为选择，不是可以留待以后实现的功能。

已由主规格方向确认的规则包括：原语义段先判 min_len、容量子段不再次丢短段；容量封闭线索不可被
pass1、rescue 或 pass2 合并；救援容量失败不自动生成业务 episode；预检承诺以已知证据为限并由
真实请求检查及提交前会话重算闭合；RNG、任务 namespace 与校准统一按 session，batch 不改变语义。
